# Sampling method — SPEDIA adapter validation sample

Generated by `validation/spedia_adapter_validation.py`. Do not edit by hand.

## Design

- **Population:** the 56,737 SPEDIA records whose `Activity` is `email`, `http`, `file` or `device` (the replay scope used in the paper).
- **Strata:** the four DLP activity categories; 50 records per stratum, 200 in total. Equal allocation, not proportional.
- **Seed:** `20261007`.
- **Procedure per stratum:** the stratum's records are sorted by the source `id` (UUID string, lexicographic, stable mergesort). This makes the order independent of file row order. A NumPy `default_rng([seed, k])` generator is created, where `k` is the fixed stratum index (email=0, http=1, file=2, device=3). It draws 50 distinct positions without replacement.
- **Fields used for selection:** `Activity` and `id` only. `Anomaly`, `Agent_name` and `User` are not read during sampling, and they are not written to `review_sample.csv`. The review is therefore blind to outcome labels and identities.
- **Reproducibility:** rerunning with the same dataset (MD5 `e01e0baaf3b523a0b493fc9c52af2b1c`) and seed yields the same 200 ids. The ids are listed in `automatic_checks.json` (`sample_ids`).

## Command

```bash
python validation/spedia_adapter_validation.py --seed 20261007
```

## Known consequence of simple random sampling within strata

The rare branches of the mapping appear only a few times, or not at all, in a 50-record stratum. Examples are cloud-list hosts (445 of 21,723 HTTP rows) and keyword-sensitive file paths. The sample therefore supports manual inspection of typical records. Every branch is still checked automatically on the full population (see `adapter_validation_report.md`). The sample was not enriched by mapping outcome. Enrichment would have required the adapter output, which is the subject of the test, as a selection variable.
