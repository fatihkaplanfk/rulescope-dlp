## 3. Category findings

### Email
- Source fields `To`, `Cc`, `Bcc` and `Attachments` (count) are present for every email row. `Action` is `Email sent` for all of them. External status and attachment presence are therefore directly observable, and the in-scope count reflects real *sent* messages with at least one attachment and at least one non-`dtaa.com` recipient.
- Not observable: attachment content or sensitivity (`data_classification=Restricted` is a research mapping), and the endpoint device (`Managed` is assumed). `dtaa.com` is treated as the only internal domain. This follows the CERT origin of the records and is an assumption, not a source label.
- `MIXED_INTERNAL_EXTERNAL_RECIPIENTS` / `EXTERNAL_ONLY_VIA_BCC` mark messages where the "any external recipient" rule decides the outcome. They are informational, not ambiguous: a message with any external recipient leaves the organization. Whether that is the intended policy reading is left to the human review.

### HTTP
- Every HTTP row has `Action = URL accedida` ("URL accessed"). No row has an HTTP method, a byte count, or an uploaded object name, and `Size*` fields are empty. **No HTTP record provides evidence of a file upload.** A cloud-list match means only that the listed service was accessed. The `CloudUpload` channel is a metadata proxy.
- Hosts matched to the cloud list (population): {'sourceforge.net': 206, 'mediafire.com': 200, 'dropbox.com': 31, 'github.com': 6, 'docs.github.com': 2}.
- Because `Size*` is absent, every HTTP event gets `size_mb = 0`. The `conflict_cloud` mutation is conditioned on `size_mb = 0`. It therefore applies to **all 445** cloud-proxy events because size metadata is missing, not because zero-byte transfers were observed. The exposure count is a correct consequence of the adapter, but it should be described as "events without size metadata".
- Hosts that look transfer-related but are not on the fixed list (diagnostic only; top entries): {'megaupload.com': 20, 'filesonic.com': 19, 'filestube.com': 19, 'files.wordpress.com': 16, 'fileserve.com': 8, 'drive.upm.es': 3}. These hosts (for example `megaupload.com`) are mapped to `Web`. The fixed list is therefore a conservative, incomplete proxy, and the cloud in-scope count is a lower bound under the stated proxy definition.
- Private-IP hosts (e.g. `10.12.x.x`) are assigned `destination_trust = Untrusted` like all HTTP rows. This does not affect any requirement scope, because non-listed hosts map to `Web`.

### File
- `File accessed` rows (CERT decoder) carry only `Filename` (e.g. `ABC123.doc`) and no `Path`. The adapter evaluates sensitivity on `Path` only, so for these rows sensitivity cannot be evaluated, and they map to `FileOperation/Internal` (`FILENAME_ONLY_SENSITIVITY_NOT_EVALUABLE`).

## 6. Limitations

1. **Shared specification.** The independent checker re-implements the published rules with different code, but it reads the same specification values: the `dtaa.com` internal domain, the 13-domain cloud list, the sensitivity keywords and the file-type domain. Both implementations share any error in that specification, such as a missing cloud domain or an over-broad keyword. Agreement shows that the code implements the written rules. It does not show that the rules are the right DLP interpretation.
2. **Common interpretation.** Both implementations were written by the same team from the same text. Ambiguous rule text could be read the same wrong way in both. The human review of `review_sample.csv` is the control for this.
3. **Unverifiable properties.** Source data cannot confirm uploads for HTTP rows, device trust for removable devices, or content sensitivity for any category. These properties are reported as `UNVERIFIABLE_PROXY` or listed in `unverifiable_attributes`, never as verified.
4. **Sample size.** 50 records per stratum give limited power for rare branches (cloud hosts, sensitive paths). The full-population automatic check covers those branches, but only against the shared specification.
5. **Source fidelity.** SPEDIA mixes CERT-derived synthetic rows with exercise logs. The validation cannot establish that source rows describe real-world transfers. It can only show that the adapter output follows from the source metadata as recorded.
