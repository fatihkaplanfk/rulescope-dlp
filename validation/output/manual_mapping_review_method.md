# Mapping-focused manual review sample — method

Generated by `validation/manual_mapping_sample.py`. It complements the 200-record general sample (`review_sample.csv`, `sampling_method.md`), which is unchanged. **No manual review has been performed.** The `human_review` and `reviewer_notes` columns of `manual_mapping_review.csv` are empty, and every count below is an automatic pre-analysis.

## Command and seed

```bash
python validation/manual_mapping_sample.py --seed 20261007
```

- Seed: `20261007`. Each draw uses NumPy `default_rng([seed, stream])` with fixed stream numbers (email 100, cloud 101 plus 110–114, device 102, file strata 130–134). These streams are distinct from the general sample's streams 0–3.
- Dataset MD5 verified before sampling: `e01e0baaf3b523a0b493fc9c52af2b1c`.
- Within every pool, records are ordered by source `id` before drawing, so the result does not depend on file row order.
- Selection variables: `Activity`, `Action`, source metadata (`To/Cc/Bcc`, `Attachments`, `Url`, `Path`, `Filename`) and the adapter's mapping outcome. **`Anomaly`, `Agent_name` and `User` are not used and are not written to the CSV.**
- Records in the 200-record general sample are excluded, so no record is reviewed twice.

## Automatic pre-analysis

Two questions are answered separately for each record:

1. **Rule-consistent** (`rule_consistent`): does the source metadata yield the normalized value under the documented adapter rule? This is checked with the independent checker in `spedia_adapter_validation.py`.
2. **Semantically verified** (`semantically_verified`): can the SPEDIA source establish the real-world security meaning of the mapped event, for example that sensitive data actually left through that channel? The columns `semantic_claim_verifiable` and `semantic_claim_not_verifiable` list the parts of the claim the source can and cannot establish.

`Semantically verified` is `false` for every record. This is not a review outcome. Each mapped DLP claim contains a component that SPEDIA does not record (content sensitivity, upload, or device trust), as listed below.

## What the source can and cannot establish

| Group | Verifiable from SPEDIA metadata | Not verifiable from SPEDIA |
|---|---|---|
| Email | `Action = Email sent`; recipient domains; whether a recipient is outside `dtaa.com`; attachment count | attachment content and sensitivity (`Restricted`); attachment names and types; that `dtaa.com` is the only internal domain; sending device (`Managed` assumed) |
| HTTP / cloud | URL accessed; hostname; membership of the fixed list | any upload (no method, byte count or upload indicator); data sensitivity (`Confidential`); destination trust; size |
| Removable device | connect vs. disconnect action; timestamp | management status (`Unmanaged` is assumed); device class; whether data was written |
| File | file action; path or filename; extension | content sensitivity; true format (extension only); directory location when Path is missing |

## Limitations to state explicitly

- **HTTP upload proxy.** Every SPEDIA HTTP record has `Action = URL accedida` ("URL accessed") and no HTTP method, request size, transferred bytes or uploaded object. A host on the cloud list is therefore evidence of *access to a file-transfer service*, never of a file upload. `CloudUpload` is a metadata proxy, and group B records must not be counted as verified uploads.
- **Fixed cloud-domain list.** The 13-domain list was fixed before the replay and is incomplete. The full-population report already shows file-hosting hosts outside the list (e.g. `megaupload.com`, `filesonic.com`, `fileserve.com`) mapped to `Web`. In-scope cloud counts are therefore a lower bound for this proxy definition. List membership also says nothing about what the user did on the service.
- **Device-trust assumption.** SPEDIA device records contain only the connect or disconnect action. `device_trust = Unmanaged` is assigned to every device by assumption. It is not a verified device property and must not be described as one.
- **Path/extension classification.** Sensitivity is inferred from path keywords only, and `file_type` from the extension only. `File accessed` records have no Path, so the sensitivity rule cannot fire for them (stratum D4/D5). Legacy `.doc` files fall outside the declared `file_type` domain and become `OTHER`. No file content is available. File mappings do not enter any declared requirement, so they do not affect Table 3.
- **Email sender domain.** 1,308 of the 1,851 in-scope email records have a sender address outside `dtaa.com`. The source labels them `Email sent`, but they may describe personal webmail rather than traffic through the corporate gateway. The adapter does not consider the sender. These records are flagged `SENDER_NOT_INTERNAL_DOMAIN` for human judgement. This observation was not part of the earlier report.
- **Shared specification.** Rule consistency is checked against the same written specification that the adapter implements. It confirms faithful implementation, not that the mapping is the right DLP interpretation. That is the purpose of the human review.

## Reviewer instructions

For each row, compare `source_*` with `adapter_*` and `mapping_rule`. Record in `human_review` one of `consistent`, `inconsistent` or `ambiguous`. In `reviewer_notes`, record whether the source supports the *security meaning* (e.g. "external recipient confirmed; content unknown"). Ideally, two reviewers work independently and their agreement is reported.

## Draft methodology text (no review results)

> In addition to a 200-record stratified sample drawn across the four activity categories, a second, mapping-focused sample was drawn to examine the adapter decisions that determine the declared protection scopes. Using a fixed seed (20261007) and excluding records already in the first sample, 25 records were selected from each of four groups. The first group consists of email records mapped to external recipients with attachments. The second consists of HTTP records whose hostname matched the fixed cloud-transfer domain list and was therefore normalized to the CloudUpload proxy; one record per matched list entry was included. The third consists of removable-device connection events. The fourth consists of file records, stratified by the presence of a path, recognized versus unrecognized extensions, keyword-based path sensitivity and filename-only legacy `.doc` records. Selection did not use the Anomaly, Agent_name or User fields. For each record, the review sheet lists the source metadata, the normalized attributes and the applied mapping rule, and it distinguishes two questions. The first is whether the normalized value follows from the source metadata under the documented rule (rule consistency). The second is whether the source data can establish the security meaning of the mapped event (semantic verifiability). The latter is not established for any group by construction: SPEDIA HTTP records contain no request method, transferred bytes or upload indicator, so a cloud-domain match denotes access to the service rather than a verified upload; device records carry no management status, so the Unmanaged attribute is an assumption; and no category provides content sensitivity. The results of the manual review are reported separately from these automatically derived properties.
